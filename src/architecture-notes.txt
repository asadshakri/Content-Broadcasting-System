ARCHITECTURE  NOTES


1. Authentication & RBAC Flow


Authentication is implemented using JWT (JSON Web Token).


Flow:-


* User registers with
   - name
   - email
   - password
   - role (principal / teacher)


* Password is hashed using bcrypt before storing in database.
* User logs in with email and password.
* If credentials are valid - JWT token is generated
 - token contains:
     {
       userId
     }
* Protected routes require token in header:
Authorization: Bearer <token>


* Middleware verifies token and loads user.
* Role Based Access Control (RBAC) middleware checks permissions.
Roles:-


Teacher:
- Upload content
- View own content
- View approved content
- Schedule approved content


Principal:
- View all content
- View pending content
- Approve content
- Reject content


Public Students:
- No login required
- Access only public live API




2. Subject-Based System Design


Each content belongs to one subject:


Examples:
- Maths
- Science
- English


System uses subject slots.----> Table: Slots


Each subject has one queue (slot)
Example: Maths Slot , Science Slot


When teacher schedules approved content, content is placed inside that subject slot.


This enables independent rotation for each subject.


Examples:
Maths Queue:
A -> B -> C


Science Queue:
X -> Y




3. Upload Handling Approach


Teachers upload content using multipart/form-data.
Fields:
- title (required)
- subject (required)
- description (optional)
- file (required)
- start_time
- end_time


Upload middleware: - multer 


Validation:
- allowed types: jpg, png, gif
- max file size : 10 mb


Flow:
*  File received by multer
* File stored temporarily in memory buffer
* Uploaded to AWS S3
* Public file URL stored in database




4. Approval Workflow Design


Content lifecycle:
uploaded -> pending -> approved / rejected


When teacher uploads: status = pending


Principal actions:


Approve:
- status = approved
- approved_by = principal id
- approved_at = timestamp


Reject:
- status = rejected
- rejection_reason


Only approved content can later be scheduled by the Teacher.


Rejected/Pending contents never appear publicly.




5. Scheduling / Rotation Logic


Scheduling happens after approval by the principal


Teacher manually schedules approved content.


Flow:


1. Teacher selects approved content
2. System finds subject slot
3. System inserts into Schedule table


Fields:
- content_id
- slot_id
- rotation_order
- duration_minutes


rotation_order is calculated dynamically by the system.


Example:


Maths Queue:
1. addition        5 min
2. subtraction    5 min
3. multiplu        10 min


Rotation Algorithm:


totalDuration = 20 min
currentMinute = floor(now in minutes) % totalDuration
Range Mapping:


0-4   => item 1
5-9   => item 2
10-19 => item 3


Then loop repeats forever.


Additional filtering before showing content:


- status must be approved
- teacher must match route teacherId
- current time >= start_time
- current time <= end_time


If no valid item: return empty response
